# Assimilation controls cleanup

**Status:** planned
**Goal:** Fix the meaningful issues found in a post-implementation review of the assimilation-controls-redesign plan (commits `4c29c72c21..1535e3c405`, already shipped on `main`): unreachable revive/remove-from-recall code left behind by that plan's own scope decisions, and an E2E coverage gap where the property panel's tracker-status link is never actually clicked.

## Design decisions

- **No backend changes.** Everything here is frontend + E2E, same as the plan this cleans up after.
- **Scope is exactly the review's high/medium findings.** Two low-severity notes from the review (renaming `noteLevelTrackerOfType`, collapsing `AssimilationSettings.vue` into `AssimilationPanel.vue`) are captured under "Not planned" below rather than forced into slices — see rationale there.
- **Why the dead code exists:** the assimilation-controls-redesign plan's slices 6 and 8 deliberately moved Revive/Remove-from-recall off the note-level and property-level panels onto the tracker detail page (`MemoryTrackerPageView.vue`), which already has its own independent revive/removeFromRecall implementation. That left `useMemoryTrackerActionHandlers.ts`'s `revive`/`removeFromRecall` handlers (and the whole of `useReviveMemoryTracker.ts`, whose only caller was that dead handler) unreachable — confirmed by grep: zero callers anywhere in `frontend/src`/`frontend/tests` call `.revive()`/`.removeFromRecall()` on what `useMemoryTrackerActions`/`useInjectedMemoryTrackerActions` return. No per-slice `post-change-refactor` pass caught it because each was scoped to its own slice's diff, and the final slice's dead-code sweep covered `frontend/src/components/recall/` but not `frontend/src/composables/`.
- **`useRemoveFromRecall.ts` is NOT dead** — `MemoryTrackerPageView.vue` uses it directly, independent of the dead handler. Only the unused import/call inside `useMemoryTrackerActionHandlers.ts` goes away in slice 1, not the file itself.
- **Property status-link E2E gap:** since slice 8 of the redesign, the property panel renders the same `AssimilationModes.vue` status-link markup as the note-level panel (including the `title="Recalled N times"` tooltip), but `propertyMemoryTrackerExpectations.ts` still reads tracker state via a backend testability call and navigates with a direct `router().push(...)`, never clicking the real `<router-link>`. The note-level equivalent (`openNoteLevelMemoryTracker`) does click the real element. Slice 2 closes that gap; slice 3 then re-evaluates the testability method's doc comment and remaining role now that recall-count can be verified through the same click-through pattern note-level already uses.

## Slices

### 1. Delete unreachable Revive/Remove-from-recall handlers from the note/property action composables

- **Type:** Structure
- **Status:** done
- **Pre-condition:** `useMemoryTrackerActionHandlers.ts`'s `revive`/`removeFromRecall` handlers and `useReviveMemoryTracker.ts` have zero callers anywhere outside themselves and `useMemoryTrackerActions.ts`'s re-export (confirmed by the review's grep pass — MemoryTrackerPageView.vue uses its own separate revive/removeFromRecall implementation).
- **Trigger:** none externally — no UI ever called these handlers; deleting them changes no observable behavior. Verified by the existing test suite staying green.
- **Post-condition:** `useMemoryTrackerActionHandlers.ts` no longer defines or returns `revive`/`removeFromRecall`, and no longer imports `useReviveMemoryTracker`/`trackersToRevive`. `useMemoryTrackerActions.ts`'s `MemoryTrackerActions` type and its return no longer include `revive`/`removeFromRecall`. `useReviveMemoryTracker.ts` is deleted (its only caller is gone). `useRemoveFromRecall.ts` is untouched — still used directly by `MemoryTrackerPageView.vue`.
- **Touches:** `frontend/src/composables/useMemoryTrackerActionHandlers.ts` (remove `revive`/`removeFromRecall` functions, their type-signature entries, the now-unused `trackersToRevive`/`useReviveMemoryTracker` import, and the now-unused `useRemoveFromRecall`/`REMOVE_FROM_RECALL_CONFIRM` import if nothing else in the file needs it), `frontend/src/composables/useMemoryTrackerActions.ts` (drop `revive`/`removeFromRecall` from `MemoryTrackerActions`), delete `frontend/src/composables/useReviveMemoryTracker.ts`. Post-change-refactor also removed `activeUnderstandingTrackers` from `frontend/src/components/recall/assimilationMemoryTrackers.ts`, which became dead once the `removeFromRecall` handler (its only caller) was deleted.
- **Tests:** re-run the full frontend unit suite (or at minimum every spec touching `AssimilationPanel*`, `RichFrontmatterPropertyPanel`, and any spec importing `useMemoryTrackerActions`/`useMemoryTrackerActionHandlers`) to confirm nothing broke; grep `frontend/src` and `frontend/tests` for `useReviveMemoryTracker`/`trackersToRevive`/`reviveMemoryTrackers` after the edit to confirm zero remaining references, and for `.revive(`/`.removeFromRecall(` on the two edited composables' return values to confirm zero call sites existed before deletion (belt-and-suspenders on the review's own grep).

### 2. Property panel's memory-tracker status link is verified by clicking the real UI element

- **Type:** Behavior
- **Status:** planned
- **Pre-condition:** the property panel (`RichFrontmatterPropertyPanel.vue`, since slice 8 of the redesign) renders `AssimilationModes`'s status-link row exactly like the note-level panel does, but no E2E scenario clicks it — `property_memory_tracker.feature`'s existing scenarios that reach a tracked property only ever read state via backend testability (`propertyMemoryTrackerForCurrentNote`) and jump to the tracker page with `router().push(...)`.
- **Trigger:** an existing (or lightly extended) scenario in `property_memory_tracker.feature` that has an actively-tracked property and opens its memory tracker.
- **Post-condition:** opening a property's memory tracker from the assimilation panel clicks the real rendered status link (mirroring `noteLevelTrackerStatusElement`'s note-level pattern) and lands on the correct tracker page; a regression that broke the property row's `router-link` (wrong route name/param, dead click handler, wrong scoping) would now fail this test.
- **Touches:** `e2e_test/start/pageObjects/assimilationPage/shared.ts` (add a property-row-scoped status-link selector/finder, reusing the existing `withPropertyPanel` scoping convention from `e2e_test/start/pageObjects/noteRichPropertyAssimilationMethods.ts` rather than duplicating it), `e2e_test/start/pageObjects/assimilationPage/propertyMemoryTrackerExpectations.ts` (`openPropertyMemoryTracker` clicks the real element instead of `router().push(...)`).
- **No new scenario needed:** `property_memory_tracker.feature`'s existing "Property memory tracker note link opens that property" scenario (line ~197) already calls the `I open the property memory tracker for "topic"` step, which resolves to `openPropertyMemoryTracker` — fixing that page-object method's implementation makes this already-existing scenario exercise the real click-through path with no feature-file change.
- **Tests:** `cypress run --spec e2e_test/features/recall/property_memory_tracker.feature` green (all scenarios, including the one above now exercising the click-through path). Follow the E2E-led-beats workflow: confirm the changed assertion fails for the right reason (wrong element/selector) before wiring the click, then make it pass.

### 3. Simplify the property tracker's interim testability read now that the UI status link is click-verified

- **Type:** Structure
- **Status:** planned
- **Pre-condition:** slice 2 shipped — `openPropertyMemoryTracker` now navigates via the real status link, and (per slice 2) recall-count assertions on the reached tracker page can use `assumeMemoryTrackerPage().expectRecallCount(count)`, the same pattern `readNoteLevelRecallCountAndReturn` already uses for note-level trackers.
- **Trigger:** none externally — this only touches E2E page-object internals and a stale comment; user-visible test outcomes are unchanged (still green).
- **Post-condition:** `propertyMemoryTrackerForCurrentNote`'s doc comment no longer claims the property status link "only ever shows navigation, not recall count" (false since `AssimilationModes.vue` puts recall count in the `title` attribute on both scopes identically). If the property recall-count assertions (`expectPropertyMemoryTracker`'s count check) can now be rewritten to click through to the tracker page and read `expectRecallCount` instead of reading the backend directly — matching the note-level pattern exactly — do so. Keep `propertyMemoryTrackerForCurrentNote`'s backend read only for the role the UI genuinely cannot provide: distinguishing "tracker never existed" from "tracker exists but `removedFromTracking`" for `expectPropertyMemoryTrackerAbsent` (the UI collapses both to "no status link, show Assimilate button" — matching `AssimilationModes.vue`'s deliberate "removed treated as no tracker" design decision from the original plan, so this is not fixable from the UI and should stay backend-based).
- **Touches:** `e2e_test/start/testabilityRecall.ts` (comment fix; possibly trim `propertyMemoryTrackerForCurrentNote`'s responsibilities if the recall-count role moves to the click-through path), `e2e_test/start/pageObjects/assimilationPage/propertyMemoryTrackerExpectations.ts` (`expectPropertyMemoryTracker`'s recall-count check, if reworked).
- **Tests:** `cypress run --spec e2e_test/features/recall/property_memory_tracker.feature` stays green (14/14, matching the redesign plan's slice 7/8 baseline).

## Not planned (considered and rejected)

- **Renaming `noteLevelTrackerOfType` to something scope-neutral** — real naming smell (it resolves both note-level and property-level trackers despite the name), but a pure rename with no behavior change and no bug risk; lower priority than the dead-code and coverage-gap fixes above. Revisit opportunistically next time `assimilationMemoryTrackers.ts` is touched rather than spending a dedicated slice on it now.
- **Collapsing `AssimilationSettings.vue` into `AssimilationPanel.vue`** — the file is thin post-redesign, but merging two components is a judgment call about future extensibility (e.g. if the note-level panel grows a second child later) rather than a clear-cut fix; not worth the risk/reward here.
