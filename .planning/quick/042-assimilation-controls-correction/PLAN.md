# Assimilation controls correction

**Status:** planned
**Goal:** Fix issues the developer found reviewing `AssimilationModes.vue` and its note-level wrapper after the assimilation-controls-redesign and its cleanup (both shipped, `.planning/quick/041-*` already removed): a UI-copy translation layer that invented terms not in ADR 0001 (and conflated two distinct domain concepts, Commissioned and MCQ), a Skip/Return-to-sequence affordance placed on the wrong row, missing visual grouping between Assimilate and Skip, a component name that no longer matches what the component does, and a layout bug that shoves the whole panel to the right instead of wrapping.

## Design decisions

- **No backend changes.** Everything here is frontend, plus a dedicated E2E-naming slice (6) that keeps test vocabulary mapped directly to the renamed production identifiers — same pattern as the two prior `041-*` plans on this feature.
- **ADR 0001 is binding, not a source to paraphrase from.** `docs/adrs/0001-ubiquitous-language.md` defines **Commissioned memory tracker** (Commissioned Learning Session section) and **Understanding memory tracker** (Assimilation section) as the domain terms for two of the three `MemoryTrackerType` values; **Spelling memory tracker** for the third. **MCQ** is a *different*, already-correctly-used ADR term (`RecallSessionOptionsDialog.vue`, `RecallPage.vue`) — "Multiple-choice content on a note" — unrelated to the Commissioned tracker type. `AssimilationModes.vue`'s `modeLabels` map (`COMMISSIONED: "MCQ"`, `UNDERSTANDING: "Comprehension"`) is being deleted for exactly this reason: it renamed one real domain term to another real-but-wrong domain term, and invented a new word for a second. The fix keeps a label lookup (Title Case is a legitimate display concern) but its values become the ADR nouns verbatim: `Commissioned`, `Spelling`, `Understanding`.
- **Skip / Return-to-sequence belongs to Understanding, not Commissioned.** ADR 0001: "**Assimilation sequence** — ... A unit is in the sequence iff it has not been skipped from the sequence and has **no live understanding memory tracker**." The sequence's membership test is defined in terms of the Understanding tracker specifically; it has nothing to do with whether a Commissioned tracker exists. The current `skipAffordanceMode` computed (COMMISSIONED-first, falling back to UNDERSTANDING only when COMMISSIONED isn't offered) was written under the same mistaken Commissioned/MCQ conflation named above — it was choosing the row by "whichever row looks like the walkthrough's default quiz," not by the domain rule. Every current caller (`AssimilationSettings.vue`: all three modes; `RichFrontmatterPropertyPanel.vue`: `["UNDERSTANDING"]` only) always includes `UNDERSTANDING` in `allowedModes`, so the fix is a straight simplification: the affordance always renders on the Understanding row, full stop — no fallback branch to keep.
- **Layout root cause (confirmed live, not just by reading code):** logged in locally (`pnpm sut` dev server, note "Earth" in the "Space topics" notebook) and opened the assimilation panel via the toolbar. At both 1456px and 700px viewport widths the three mode rows sit hard against the panel's right edge with a large empty gap on the left, and do not reflow — this is `AssimilationSettings.vue`'s inner wrapper (`class="flex flex-wrap items-stretch justify-end gap-2 sm:flex-1"`) inside an outer two-column `sm:flex-row sm:justify-between` scaffold. Both classes date from when that left/right split held a settings toggle next to the modes; the toggle is gone (per the redesign's own "drop panel heading and progress summary" step) but the two-column scaffold and its `justify-end` were never removed, so the sole remaining child gets pushed to the container's trailing edge. `RichFrontmatterPropertyPanel.vue`'s wrapper (`"pl-8 flex flex-wrap items-center gap-2 gap-y-1"`) is the already-correct sibling pattern to mirror — a flat, left-aligned, wrapping flex row.
- **Component rename maps directly, everywhere — no separate test vocabulary.** `AssimilationSettings.vue` → `NoteAssimilationModes.vue` is the developer's explicit ask ("the component name... it need to be renamed"). Its `data-testid`/`aria-label` ("assimilation-settings" / "Assimilation settings") and the composable state that gates it (`useAssimilationView.ts`'s `showAssimilationSettings`/`closeAssimilationSettingsIfOpen`) carry the same wrong word and are fixed alongside it. The note toolbar's "more options" menu item text (`noteMoreOptionsTitles.assimilation`, currently `"Assimilation settings"`) is genuinely user-visible copy with the identical problem, renamed to **"Assimilate"** — already-established ADR 0001 vocabulary (the Assimilation section's action verb, and the exact word the left-nav "Assimilate" item already uses for this same feature area), not a new invented term. The developer explicitly rejected keeping a separate, drifted vocabulary in the E2E layer once production naming changes: the page-object method `openAssimilationSettings()`, its sibling `expectAssimilationSettingsAbsent()`, the step_definitions file `assimilation_settings.ts`, and every Gherkin step phrase built on "assimilation settings" (~20 call sites across `property_memory_tracker.feature`, `assimilation_walkthrough.feature`, `commissioned_learning_session.feature`) all get the same direct rename, converging on **"assimilation panel"** — the term that already names the gating component (`AssimilationPanel.vue`) and its composable exports (`showAssimilationPanel`/`closeAssimilationPanelIfOpen`). Production and test vocabulary must describe the same concept with the same words. This spans two slices: slice 5 is the user-facing/production rename (Behavior — the menu text changes); slice 6 is the E2E-only rename that keeps test vocabulary mapped to it directly (Structure — no behavior change, existing scenarios keep passing under new names).

## Slices

### 1. Mode row labels are ADR 0001's own domain nouns, not invented UI words

- **Type:** Behavior
- **Status:** done
- **Pre-condition:** `AssimilationModes.vue`'s `modeLabels` map renders `"MCQ"` for a Commissioned-tracker row and `"Comprehension"` for an Understanding-tracker row — neither word appears anywhere in ADR 0001's glossary; `"MCQ"` is actively misleading because ADR 0001 already defines MCQ as a different concept (multiple-choice recall-prompt content).
- **Trigger:** the assimilation panel renders a mode row for `COMMISSIONED` or `UNDERSTANDING`.
- **Post-condition:** the row label reads exactly `"Commissioned"` for `COMMISSIONED` and `"Understanding"` for `UNDERSTANDING` (Title Case of ADR 0001's "Commissioned memory tracker" / "Understanding memory tracker"); `"Spelling"` for `SPELLING` is unchanged. No occurrence of `"MCQ"` or `"Comprehension"` remains anywhere in `AssimilationModes.vue` (code or comments).
- **Touches:** `frontend/src/components/recall/AssimilationModes.vue` (`modeLabels` values; the code comment on `skipAffordanceMode` that says "Comprehension (UNDERSTANDING)" — update or drop when slice 2 rewrites that logic anyway, whichever lands first), `frontend/tests/components/recall/AssimilationModes.spec.ts` (the `it.each` label-mapping test at the bottom: `["COMMISSIONED", "MCQ"]` → `["COMMISSIONED", "Commissioned"]`, `["UNDERSTANDING", "Comprehension"]` → `["UNDERSTANDING", "Understanding"]`).
- **Tests:** `pnpm frontend:test tests/components/recall/AssimilationModes.spec.ts`. Grep `frontend/src/components/recall/AssimilationModes.vue` for `MCQ`/`Comprehension` after the edit to confirm zero remaining occurrences.

### 2. Skip / Return-to-sequence only ever appears on the Understanding row

- **Type:** Behavior
- **Status:** done
- **Pre-condition:** `skipAffordanceMode` puts the Skip/Return-to-sequence affordance on the `COMMISSIONED` row whenever Commissioned is offered (note-level panel today), falling back to `UNDERSTANDING` only for scopes that never offer Commissioned (property-level panel). Per ADR 0001 the assimilation sequence's membership rule is about the Understanding tracker specifically ("no live understanding memory tracker") — Commissioned assimilation is a separate, optional path with nothing to do with sequence membership, so Skip does not belong on that row at all, with or without a fallback.
- **Trigger:** the assimilation panel renders with `UNDERSTANDING` in `allowedModes` (true for every current caller: note-level `AssimilationSettings.vue` and property-level `RichFrontmatterPropertyPanel.vue`).
- **Post-condition:** the Skip / Return-to-sequence affordance renders on the `UNDERSTANDING` row only, regardless of whether `COMMISSIONED` is also allowed. The Commissioned row never shows Skip or Return-to-sequence.
- **Touches:** `frontend/src/components/recall/AssimilationModes.vue` (delete the `skipAffordanceMode` computed; `rows`'s `showSkipAffordance` becomes `mode === "UNDERSTANDING"` directly), `frontend/tests/components/recall/AssimilationModes.spec.ts` (replace `"puts the Skip / Return-to-sequence affordance on the MCQ row when allowed"` — assert Skip is on the Understanding row and absent from the Commissioned row, for a mount that allows both; delete/merge the now-meaningless `"falls back... to the Comprehension row when MCQ isn't allowed"` fallback test into that same assertion since there is no more fallback branch to distinguish; change the two mounts in `"shows Return to sequence instead of Skip..."` and `"emits skip and returnToSequence"` from `allowedModes: ["COMMISSIONED"]` to `allowedModes: ["UNDERSTANDING"]`, since a Commissioned-only mount no longer has an Understanding row to host these controls).
- **Tests:** `pnpm frontend:test tests/components/recall/AssimilationModes.spec.ts`.

### 3. Assimilation panel rows stay left-aligned and wrap instead of drifting right

- **Type:** Behavior
- **Status:** done
- **Pre-condition:** confirmed live at 1456px and 700px viewport widths (dev server, note "Earth" in "Space topics") — the three mode rows sit flush against the panel's right edge with a large empty gap to their left, and do not reflow onto more lines as the window narrows. Root cause: `AssimilationSettings.vue`'s two-column wrapper (`flex flex-col gap-3 sm:flex-row sm:items-center sm:justify-between` outer, `flex flex-wrap items-stretch justify-end gap-2 sm:flex-1` inner) was built for a left/right split (modes vs. a settings toggle) that no longer exists — the sole remaining child (`<AssimilationModes>`) gets pushed to the trailing edge of its `flex-1` slot by `justify-end`.
- **Trigger:** the note-level assimilation panel renders, at any viewport width.
- **Post-condition:** the panel's rows start flush left, and individual rows wrap onto additional lines (rather than overflowing or staying pinned right) when the window is too narrow to fit them on one line — matching `RichFrontmatterPropertyPanel.vue`'s existing wrapper pattern (`flex flex-wrap items-center gap-2`), the already-correct sibling implementation for the same `<AssimilationModes>` component at property scope.
- **Touches:** `frontend/src/components/recall/AssimilationSettings.vue` (flatten the two nested wrapper divs into one `flex flex-wrap items-center gap-2` container around `<AssimilationModes>`; the outer `<section>`'s own `flex flex-col gap-0` can stay or collapse into the same div — whichever keeps the file simplest given it's a single child now).
- **Tests:** `pnpm frontend:test tests/components/recall/AssimilationPanel.spec.ts tests/notes/NoteToolbar.assimilationPanel.spec.ts` (confirm nothing currently pins the removed classes — none do, per grep). Manually verify in-browser (dev server, any note) at a normal width and a narrow (~700px) width: rows start at the panel's left edge and wrap rather than overflowing right.

### 4. Skip / Return-to-sequence is visually grouped with its Assimilate button

- **Type:** Behavior
- **Status:** done
- **Pre-condition:** on a row with the skip affordance, "Assimilate" and "Skip" (or "Return to sequence") render as two separately-spaced buttons with no shared visual container — nothing ties the skip action to the specific mode/button it skips, which is confusing once a row can show both.
- **Trigger:** a mode row shows both its Assimilate button and the Skip/Return-to-sequence affordance (i.e. the Understanding row, per slice 2).
- **Post-condition:** Assimilate and Skip/Return-to-sequence render as one joined button group (using this codebase's existing `daisy-join`/`daisy-join-item` convention, already used for grouped controls in `RelationTypeSelect.vue` and `InputWithType.vue`) so the pairing reads as one unit. Rows without the skip affordance are visually unchanged (a lone Assimilate button, not wrapped in a join).
- **Touches:** `frontend/src/components/recall/AssimilationModes.vue` (wrap the Assimilate + Skip/Return-to-sequence template block in a `daisy-join` container when `row.showSkipAffordance`, with `daisy-join-item` on each button), `frontend/tests/components/recall/AssimilationModes.spec.ts` (new assertion: when the skip affordance is shown, the Assimilate button and the Skip button share a common `.daisy-join` ancestor element).
- **Tests:** `pnpm frontend:test tests/components/recall/AssimilationModes.spec.ts`.

### 5. Note-level assimilation entry point no longer calls itself "settings"

- **Type:** Behavior
- **Status:** done
- **Pre-condition:** `AssimilationSettings.vue` (the note-level wrapper around `<AssimilationModes>`) contains no settings — its only job, since the redesign, is supplying `allowedModes: [COMMISSIONED, SPELLING, UNDERSTANDING]` and wiring events — yet its filename, `data-testid`, `aria-label`, the composable that gates its visibility (`useAssimilationView.ts`'s `showAssimilationSettings`/`closeAssimilationSettingsIfOpen`), and the note's "more options" menu item that opens it (`noteMoreOptionsTitles.assimilation`, visible text `"Assimilation settings"`) all still say "settings".
- **Trigger:** a developer reads the component/composable names, or a user opens a note's "more options" menu.
- **Post-condition:** the component file is `NoteAssimilationModes.vue` (`data-testid="note-assimilation-modes"`, `aria-label="Assimilation modes"`); `useAssimilationView.ts` exports `showAssimilationPanel`/`closeAssimilationPanelIfOpen` in place of the `...Settings` names (other exports — `isOpenForNote`, `openForNote`, `resetForNote`, `dismiss`, `toggle` — are unaffected, they never had "settings" in the name); the "more options" menu item reads **"Assimilate"** (ADR 0001's own verb for this feature area, already used by the left-nav item) instead of "Assimilation settings". No production code or test contains the string `"assimilation-settings"` or `"Assimilation settings"` afterward.
- **Touches:** `frontend/src/components/recall/AssimilationSettings.vue` → renamed `frontend/src/components/recall/NoteAssimilationModes.vue`; `frontend/src/components/recall/AssimilationPanel.vue` (import/usage update); `frontend/src/composables/useAssimilationView.ts` (the two renamed exports); `frontend/src/components/notes/widgets/noteMoreOptionsTitles.ts` (`assimilation: "Assimilation settings"` → `"Assimilate"`); `e2e_test/start/pageObjects/noteMoreOptionsForm.ts` (`titles.assimilation` value only, kept in sync with the production string it clicks by — the method name itself is slice 6's job); test files referencing any of the above: `frontend/tests/composables/useAssimilationView.spec.ts`, `frontend/tests/composables/useGoToNextAssimilation.spec.ts`, `frontend/tests/notes/NoteToolbar.assimilationPanel.spec.ts`, `frontend/tests/components/recall/AssimilationPanel.spec.ts`, `frontend/tests/notes/NoteMoreOptionsForm.spec.ts`.
- **Sizing note:** touches ~9 files across component, composable, and five spec files, plus one e2e page-object string — if it runs past the ~10 min hard trigger, split by concern in this order: (a) component file rename + testid/aria-label + its own spec-file references, (b) composable export rename + its two spec files, (c) menu-item text + e2e string + `NoteMoreOptionsForm.spec.ts`/`NoteToolbar.assimilationPanel.spec.ts`.
- **Tests:** `pnpm frontend:test tests/composables/useAssimilationView.spec.ts tests/composables/useGoToNextAssimilation.spec.ts tests/notes/NoteToolbar.assimilationPanel.spec.ts tests/components/recall/AssimilationPanel.spec.ts tests/notes/NoteMoreOptionsForm.spec.ts`. Targeted E2E for the menu-item text change: `cypress run --spec e2e_test/features/assimilation/assimilation_walkthrough.feature` (uses the "I open assimilation settings" step, which clicks by the now-renamed title text — this is the scenario most likely to break if the e2e-side string isn't kept in sync; slice 6 renames this step's own phrasing, but that comes after, so this slice must still pass under the *old* step name pointing at the *new* title text).

### 6. E2E vocabulary maps directly to the renamed assimilation panel — no drifted test-only naming

- **Type:** Structure
- **Status:** done
- **Pre-condition:** slice 5 shipped — production naming now says "assimilation panel" (`AssimilationPanel.vue`, `showAssimilationPanel`/`closeAssimilationPanelIfOpen`, menu text "Assimilate"). The E2E layer still calls the same concept by the old, now-orphaned "assimilation settings" vocabulary: page-object methods `openAssimilationSettings()` / `expectAssimilationSettingsAbsent()`, the step_definitions file `assimilation_settings.ts`, and every Gherkin step/scenario title built on the phrase "assimilation settings" (`property_memory_tracker.feature`, `assimilation_walkthrough.feature`, `commissioned_learning_session.feature`).
- **Trigger:** none externally — this only renames E2E identifiers, step phrasing, and one file name; every scenario's actual tested behavior is unchanged (still green under its new name).
- **Post-condition:** E2E vocabulary maps 1:1 to production vocabulary: `openAssimilationSettings()` → `openAssimilationPanel()`, `expectAssimilationSettingsAbsent()` → `expectAssimilationPanelAbsent()`, `assimilation_settings.ts` → `assimilation_panel.ts`, and every Gherkin step phrase/scenario title reads "assimilation panel" instead of "assimilation settings" (e.g. "I open assimilation settings" → "I open the assimilation panel"; "I am viewing assimilation settings for note {string}" → "I am viewing the assimilation panel for note {string}"; "I should not see assimilation settings" → "I should not see the assimilation panel"; scenario title "Remove from recall on assimilation settings for a property" → "Remove from recall on the assimilation panel for a property"). No file under `e2e_test/` contains the string "assimilation settings" afterward.
- **Touches:** `e2e_test/step_definitions/assimilation_settings.ts` → renamed `e2e_test/step_definitions/assimilation_panel.ts` (step phrase text updated); `e2e_test/start/pageObjects/noteMoreOptionsForm.ts` (method rename); `e2e_test/start/pageObjects/noteConversationAndQuestionMethods.ts`, `e2e_test/start/pageObjects/noteRichPropertyAssimilationMethods.ts`, `e2e_test/step_definitions/recall_memory_tracker.ts`, `e2e_test/step_definitions/assimilation_memory_tracker.ts`, `e2e_test/step_definitions/assimilation.ts` (call-site renames); `e2e_test/features/recall/property_memory_tracker.feature`, `e2e_test/features/assimilation/assimilation_walkthrough.feature`, `e2e_test/features/learning_session/commissioned_learning_session.feature` (Gherkin step/scenario-title text).
- **Sizing note:** ~10 files, all mechanical find/replace (identifier and prose renames, no logic changes) — if it runs past the ~10 min hard trigger, split by feature file (property_memory_tracker.feature's ~13 occurrences are the bulk of it; the other two feature files are a handful of lines each and can land as one follow-up cut).
- **Tests:** `cypress run --spec "e2e_test/features/recall/property_memory_tracker.feature,e2e_test/features/assimilation/assimilation_walkthrough.feature,e2e_test/features/learning_session/commissioned_learning_session.feature"` all green under the new names. Grep `e2e_test/` for `assimilation settings`/`AssimilationSettings`/`assimilation_settings` (case-insensitive) after the edit to confirm zero remaining occurrences.
