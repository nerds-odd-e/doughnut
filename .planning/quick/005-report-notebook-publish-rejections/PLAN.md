# Explain why a notebook publication was rejected

Source: [SEED-009, Story 2](../../seeds/SEED-009-git-backed-local-notebook-workflow.md#story-2),
and the completed [publish plan](../004-publish-local-note-content/PLAN.md).
Status: planned. Generated by execution-retrospective; not executed.
Readiness: ready for direct execution; sizing remains a hypothesis.

## Story contract

A notebook owner whose committed local edit is rejected needs the actual reason
so they can correct the content or understand a synchronization conflict.

Example: the accepted Git head matches the checkout, but a web edit has changed
the current projection → `donut notebook publish <directory>` → a nonzero exit
displays the server's projection-drift explanation. The local commit, refs,
index, and worktree remain intact.

The same response-presentation contract applies to invalid Markdown, unsupported
tree changes, and a publication losing the race after its initial download.
Success and 401/403 permission-denial behavior remain supported.

This corrects the original story's actionable rejection path. It adds no pull,
merge, rebase, automatic retry, server validation policy, or synchronization
capability. CI watcher improvements are separate process proposals and are not
included here.

## Confirmed finding and implementation evidence

- `cli/src/commands/notebook/notebookPublishSubmission.ts` discards every
  non-success body except the special handling for 401/403, returning only
  `{ accepted: false }`.
- `cli/src/nonInteractiveCli.ts` maps that result to the retired claim that
  publishing is not implemented. Thus 400/409 rejection reasons never reach
  the user through the intended command.
- `CustomRestExceptionHandler.handleResponseStatusException` already serializes
  the server reason as `ApiError.message`; `ControllerSetup` serializes
  authored-property `ApiException` bodies. No backend change is indicated.
- The submission suite explicitly asserts the interim 501 behavior. Binding,
  readiness, and ancestry suites also retain successful-eligibility fixtures
  and expectations described as the current interim refusal. These are residue
  from an earlier slice, not the completed product contract.
- The defect exists both at reviewed HEAD `dd1ca6415a` and in the clean working
  tree inspected for this retrospective.

## Ordered slices

### 1. Report the server's reason for rejecting publication
Type: Behavior
Status: planned
Proof: `CURSOR_DEV=true nix develop -c pnpm -C cli exec vitest run tests/notebookPublish.test.ts tests/notebookClone.test.ts`.

Behavior: an eligible bound checkout receives a rejected publication response
→ publish → report its actionable reason and exit unsuccessfully while leaving
the local checkout intact.

Replace the interim submission result/fallback with the smallest coherent error
propagation through the existing CLI exception presentation. Read the actual
API error message; when it is unavailable, include the HTTP status without
claiming the feature is unimplemented. Preserve explicit permission denial.
Follow the existing raw-fetch error handling precedent in
`cli/src/backendApi/donutBackendClient.ts` where useful; avoid introducing a
generic response framework.

Update the obsolete submission assertion and all affected eligibility fixtures,
test names, and comments to the shipped success/rejection contract. Use successful
POST fixtures where a test only needs to show that eligibility reaches submission;
keep assertions of the relevant eligibility decision and local-state preservation.
Remove historical-only assertions instead of adding tests whose sole purpose is
to say that the old message no longer exists.

Sizing: about five minutes plus focused verification, medium confidence. One
CLI response-presentation outcome and one existing proof family; no Structure
leaf is needed. Apply the normal five/ten-minute scrutiny during execution.

## Decisions and wrap-up

- ADR 0001 governs terminology; ADR 0006 favors propagating or improving useful
  failure messages. No architectural policy change is needed.
- No API generation, backend suite, migration, or broad E2E run is indicated.
- Execution uses the usual fresh post-change-refactor, one coordinator formatting
  pass, plan update, commit, push, and asynchronous CI handling. This document
  authorizes no execution during the retrospective.
