## Goal and scope

Returning learners retain recent searches without sending that history in
cookies. When an oversized request still prevents login, the server response
itself explains how to regain access. Prevention and recovery are one story,
with separately stop-safe delivery leaves.

Preserve valid legacy search history, newest-first ordering, deduplication,
100-entry and 512-character bounds. Persist future history in localStorage;
expire the old history cookie only after successful preservation. Local data
takes precedence over stale legacy data. Run migration on an app visit before
authentication-dependent requests, not only after opening search. Storage
failure must not obstruct ordinary search or login or cause cookie fallback.

Provide a self-contained, readable browser 400 recovery page for the observed
Tomcat header rejection, with a neutral heading, homepage link, fresh-login,
Private-tab, and affected-site cleanup instructions. Explain the possible loss
of sessions, preferences, and local history from manual cleanup. Retain HTTP
400 and avoid automatically retrying OAuth callbacks or clearing browser data.

Excluded: larger header limits, cache management, automatic session/unrelated
cookie deletion, new history UI or synchronization, a general browser-storage
framework, OAuth changes, a new API endpoint, redesign of application JSON
validation errors, and errors generated by an upstream service before the
request reaches Tomcat. The original iPad cookie contents remain unknown; do
not describe 200 MB of website data as the request size.

## Evidence and refinement learnings

9 KB → bare 400; affected-site cleanup restored the developer's login.
It proves the reported failure, not the future implementation.

  use the existing browser runner for the actual backend document.
- Existing SearchForm and DonutApp tests already provide the two user
  boundaries; the storage change does not need a general adapter framework.

These findings replace the previously open placement/rendering choices with
bounded execution paths. Real runtime confirmation belongs to leaves 1–2,
not this refinement task. No feature code or tests were added or run.
