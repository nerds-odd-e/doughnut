Local AI notebook effort: closing review

Range 23f081f05b..5a4bfe2f92 767 commits, 1,191 files 2026-09-20 → 2026-09-27 Reviewed 2026-09-27

This review covers the effort to let local AI IDEs work in Git checkouts of Donut notebooks, and to hold images and other non-Markdown files as folder files that Web Donut can browse, download and delete. Each finding cites its evidence and carries an urgency: queue now means urgent and important; not now means leave it off the backlog for now.

Architecture

Structural impact. The effort left the notebook as one directly modelled tree with a single byte store, a single reader and a single accepted-change owner. The legacy image, attachment-blob and Book byte stores, the representation marker, and the raw-Git paths are gone. What remains is mostly local cohesion: a few rules are still written in more than one place.

  • queue now Two improvements. Moving a folder to another notebook bypasses the one name owner. Portable path classification has no single owner, and the CLI copy has already drifted from the server.
  • not now 20 improvements, grouped by North Star topic below.
  • North Star: two topics are realized and can be retired at wrap-up; three are partly realized and can be narrowed to the gaps named here. This review does not change .planning/NORTH-STAR.md.

One set of names per folder

partly · narrowNorth Star; notebook-git-attachments.md#one-set-of-names-per-folder; ADR 0006
  • The owner exists: FolderSiblingNameValidation.entryHolding (:59-110) answers from live rows across folders, notes (Title.md) and files, ignoring letter case.
  • Note create, rename, move and restore; folder create, rename, move, trash, dissolve and merge; picture upload; Book attach; and carrying a picture along with a moved note all go through it (cca87525eb, 02a3729174, 46f53bedbe, f907bcf8b0, 38bd1e731e, 3eb37f5ade).
  • Folder-content cascades were restricted (6e2078cfde, V300000348). Permanent folder delete removes content in code.
  • queue nowRoute moving a folder to another notebook through the one name owner
    Problem
    moveFolderToAnotherNotebook is the last web placement outside the owner. It uses the old mergeTargetOrRejectConflict, which compares folder names exactly and looks at folders only. On merge it calls subtree.mergeInto, which skips the check of every destination (requireContentsFit). A folder foo moving onto Foo, or onto a file named foo, goes undetected. Clashing notes are moved unchecked, and only the case-sensitive unique keys stop them, as a 500 error or as case-variant siblings.
    Why now
    It can store siblings that differ only by letter case, which breaks checkouts on case-insensitive file systems. That is the exact harm the topic exists to prevent.
    Fix
    Use mergeTargetOrRefuse, and route the merge through the checked mergeWithinNotebook-style path against the destination notebook. Then delete mergeTargetOrRejectConflict.
    Evidence
    FolderMoveRelocation.java:141-148, FolderSubtree.java:120-126, 3d5c1bf394.
    Serves
    One set of names per folder; ADR 0006 (refuse clearly, not with a database error).
  • not nowRetire the exact-match, folder-only sibling API
    Problem
    The requireNoConflictingSibling overloads and findCandidateChildContainers (FolderSiblingNameValidation.java:176-243) give "name taken" a second meaning. Folder creation checks twice (FolderConstructionService.java:95 after WebFolderCreationService.java:44). The Git proposal path reuses it (NotebookGitProposalFolderPlacement.java:29).
    Fix
    Delete them after the item above, and rely on requireFolderNameFree at the entry points.
    Serves
    One concept, one place.
  • not nowOne "first free name" operation
    Problem
    The numbered-name policy is put together separately in five places: firstFreeFolderName, NoteMotionService:25-35, MovedNotePicture:92-99, BookSourceFilePlacement:33-39, plus NumberedNameSelection.
    Fix
    One owner method, such as firstFreeName(notebook, parent, preferred, …).
    Serves
    A name Donut chooses is the first free one.
  • not nowMake a forgotten note under a deleted folder fail loudly
    Problem
    fk_note_folder … ON DELETE SET NULL (V100000000__baseline.sql:446) would silently move notes to the root if a folder delete forgot them. That bypasses the name owner and change capture.
    Fix
    A migration to ON DELETE RESTRICT, matching V300000348.
    Serves
    "A forgotten one fails loudly" (owner decision 2026-09-26).
  • not nowLet the server choose the folder for a new relationship note
    Problem
    frontend/src/utils/relationshipFolderResolve.ts:30-56 finds or creates the child folder on the client, matching case-sensitively (:36). The folder and the note are two separate accepted changes. This predates the range.
    Fix
    Note creation takes the placement choice and resolves it on the server through the owner, in one accepted change.
    Serves
    One set of names per folder; One accepted-change boundary.

Realized? Partly. Narrow the topic to the cross-notebook move and the old API, and retire it once they land.

One format boundary

partly · narrowNorth Star; ADR 0004 §Validation
  • Everything an owner can observe holds. Markdown or file is decided by path on the server. File bytes are kept exactly (NotebookGitProposalAcceptance.java:76-100). Invalid Markdown is rejected, never demoted to a file. There are no special cases for AI guidance files: no AGENTS.md, SKILL.md or .claude/ anywhere in the source.
  • Browsing, lint and export read the projected rows. They never reclassify paths.
  • The "one classifier" is loose static predicates on NotebookGitProposalTreeShape.java:142-159. Raw .md and README.md checks are repeated in each tree walker (8 inline checks in services/notebookGit).
  • queue nowOne path-kind classifier for the Portable tree, used by server and CLI
    Problem
    Note, folder Readme, file, empty-folder marker and Git metadata are decided by string checks copied into about six walkers (NotebookGitProposalTreeShape, …MarkdownFormat.java:61, …NoteCorrespondence.java:125, …TreeInspection, …DocumentApplication.java:50-56). The CLI keeps its own copy for picking LFS uploads, and it has already drifted. It treats a root .keep as structural (cli/…/notebookPublishLfsSelection.ts:8), while the server's isEmptyFolderMarker matches only /.keep (NotebookGitProposalTreeShape.java:143) and so treats a root .keep as a file. Markdown detection is also case-sensitive (NOTES.MD becomes a file), while link resolution is not (PathShapedTarget.java:114-116).
    Why now
    The two sides already disagree about what a path is. That is a correctness defect at the boundary the topic promises is single, and each new walker copies the checks again.
    Fix
    One PortablePathKind classify(path) on a small domain class that every walker uses. Settle root .keep and .md letter case there. The CLI stops classifying and picks uploads by parsing changed blobs as LFS pointers, leaving admission to the server.
    Evidence
    Paths above; edb4990c3c, 53bf499f7a, 7c96542978, f7a12d5f8c.
    Serves
    One format boundary; ADR 0004 §Validation.
  • not nowValidate proposed Markdown in one pass
    Problem
    Strict format (NotebookGitProposalMarkdownFormat, called from three places), authored properties (AuthoredNoteContent.assertValidForSave) and the Readme type (NotebookGitProposalTypedPath.requireReadme) run in different steps. One publish can walk the tree more than once. Frontmatter is parsed both by SnakeYAML and by Frontmatter.parse.
    Fix
    One "validate proposed Markdown" pass per publish, before any branching.
    Serves
    ADR 0004 §Validation.
  • not nowOne owner for editing frontmatter in place
    Problem
    TypeScript (frontend/src/utils/noteContentInPlaceEdit.ts) and Java (algorithms/FrontmatterInPlaceEdit.java) both implement "change only the affected lines". docs/note-content-saving.md:52-63 only says they behave the same way.
    Fix
    Pick one owner, or make the rule a shared contract with cross-language test cases.
    Serves
    One format boundary. This is large and touches live-editing latency.

Realized? Partly. The behavior holds, but the structural promise of one classification owner does not. Narrow the topic to that one gap and retire it when the classifier lands.

One accepted-change boundary

partly · narrowNorth Star; ADR 0002; notebook-git-synchronization.md#domain-operation-ownership
  • Only three places write the accepted ref: web changes (AcceptedWebChangeService.java:114-122), local publish (NotebookGitProposalAcceptance.java:65) and binding creation (NotebookGitCutoverService.java:133). Every web file operation runs inside AcceptedWebChangeService.apply. A row and its image: land in one commit.
  • The web commit is built from the changed rows only (a061808c28). Touching a notebook the owner did not lock fails loudly with a 409 (bc9a0ab229, 44a3f8ceb6).
  • Local publish sets files from the proposed tip in one final pass (NotebookGitProposalAcceptance.java:79-110). LFS objects upload before the bundle. Admission accepts fast-forward only (f39ac36240). No catch swallows a failure.
  • not nowApply a local publication's notes and folders once
    Problem
    NotebookGitProposalPublisher.java:109-190 sorts note and folder changes into relocation and residual. It can apply documents twice and check the tree against the projection up to three times. This predates the range (the effort made it 36 lines shorter), but it grows with each publish story (e9518c0a83, 2466efda03).
    Fix
    Use the same final-set approach as projectAttachments: derive note and folder identities once and apply the result once.
    Serves
    ADR 0002 final-state projection; "never a classification of accepted change kinds".
  • not nowTreat a missing Git binding as impossible
    Problem
    Every notebook is Git-backed from creation, yet the owner keeps optional-binding branches (AcceptedWebChangeService.java:69-71, 87-90). Picture upload has its own missing-binding refusal (WebNoteImageUploadService.java:63-65), while Book attach has none.
    Fix
    Fail loudly in the owner, and drop the upload-specific check.
    Serves
    Keep it simple; ADR 0006.
  • not nowDecide free names and single Book under the owner's lock
    Problem
    The free-filename check (WebNoteImageUploadService.java:66) and "notebook has no Book yet" (AttachBookService.java:64) run before the binding lock. A race ends in a constraint error, not the intended refusal.
    Fix
    Move both into the operation closure. Bytes are still stored first.
    Serves
    Domain-operation ownership.
  • not nowRemove the final-newline conflict absorber in pull
    Problem
    cli/…/notebookPullRebase.ts:98-124 resolves .md conflicts that differ only by a final newline (59bc500ec6, before the range). That is a replay rule outside Git, against "Git's rebase alone decides what replays", and no architecture document mentions it.
    Fix
    Check that web saves and local files encode the final newline the same way, then delete it.
    Serves
    One accepted-change boundary.

Realized? Partly. It holds fully for files. Retire the file-specific wording, and keep one line that says "apply a publication once, with no change-kind classification" until the publisher item lands.

Coverage judgment

  • High level (E2E). Every main user path has at least one scenario: clone, pull, publish, the size limit, version recovery, and web browse, download, delete and upload. The effort's own features live in notebooks/notebook_files, cli/cli_notebook_lfs and cli/cli_notebook_attachment_size_admission.
  • Low level (unit). Backend coverage is thorough and organized by behavior (about 20 attachment controller test classes). CLI LFS unit tests cover the failure paths E2E does not, which is a good split. Frontend coverage is thin but proportionate.
  • Over-testing. Three cli_notebook_lfs scenarios repeat the clone-then-publish-several-versions setup; "Three incompressible LFS versions…" is mainly a traffic measurement and is the best candidate to fold or drop. Size-limit tests are spread over four backend classes plus NotebookGitPublishCostControllerTest. Both belong in .planning/test-optimization-candidates.md when the owner next runs test optimization.

Named gaps

  • not nowBoth sides change the same file on pull

    No test pauses a rebase on an LFS pointer conflict. This is standard Git behavior, so Donut adds little risk.

  • not nowInvalid Markdown, AI guidance included, rejected at local publish

    No E2E. The backend covers the general rule well, and a test named after AGENTS.md would only repeat it.

  • not nowA web note move carrying its picture

    Backend only, including renumbering on a clash.

  • not nowFolders holding files: dissolve, merge, permanent delete, cross-notebook refusal

    Backend only. The cross-notebook name-owner fix queued from the Architecture section brings its own proof.

  • not nowBook source change and raw file refused on publish

    Unit tests only.

  • not nowA folder holding only files is not reported empty

    Backend only.

  • not nowPicture upload refusal messages

    No frontend test shows them to the user.

  • not nowLegacy picture migration

    No retained test, by design: the one-time migration is finished and its code removed.
