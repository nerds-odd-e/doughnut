# Validate recall question integrity

**Identity:** SEED-073#validate-recall-question-integrity
**Source:** [selected story](../../seeds/SEED-073-learning-refinement-and-retrieval.md#validate-recall-question-integrity)
**Source review:** [source-review.md](source-review.md)

## Outcome and boundaries

The product owner receives, for each failure class (repeated choices, a
unique correct answer rejected by the stored key, more than one defensible
answer) and each route (generated on demand, generated by the hourly batch,
stored earlier), whether the failure can still reach a learner today, which
checks detect it, which sound questions those checks flag, what the learner
saw, and a recommendation: proceed to design, narrow and retest, or stop.

The story's restrictions apply to every slice:

- Nothing is written to Production. Production is read through read-only
  requests with the owner's CLI token only.
- Private recall evidence stays in the local cache at
  `~/git/doughnut/.planning/tmp/recall-history/`; this story's working files
  go in its `integrity/` folder. Planning files receive counts, dates, row
  numbers, and de-identified examples only.
- Paid model calls happen only under the owner's authorization, for at most
  60 verifier calls.

No product or test source is committed. Scratch tests run in the execution
workspace and are reverted before any commit, so the committed change is
planning files only and needs no formatter, API generation, or product test
gate. The story's deferred promises are excluded: no repair, no age limit
for stored questions, no verifier at generation, no flagged-question
experience, no error-rate estimate, no spelling questions, and no judgment
of keys that are wrong because the note is wrong.

## Architecture and reuse

PFE: everything this validation needs already exists; no product
responsibility is added or moved.

- Generation checks: `GeneratedMcq.isValid()` and
  `GeneratedQuestionPostProcessor`, shared by the on-demand route
  (`McqService.generateAFeasibleQuestion`) and the batch route
  (`QuestionGenerationBatchRowImportService`).
- Verifier: `NoteQuestionGenerationService.evaluateQuestion` builds the
  request; `QuestionEvaluation.getQuestionContestResult` decides.
  `NoteQuestionGenerationServiceTests` already captures that request, and
  `StructuredResponseCreateParamsSerializer.toBodyMap` renders a request
  body. The replay reuses both so the paid call carries the product's own
  request.
- Stored route: `RecallPromptService.generateAQuestion` returns the newest
  unanswered, uncontested stored question;
  `MemoryTrackerRecallPromptControllerTest` covers that reuse.
- Evidence tooling: the cache already holds the 100-day MCP export and the
  2026-11-14 key-hidden review scripts (`offline-replay/prepare.py`,
  `offline-replay/compare.py`).

Accepted decisions: [ADR 0003](../../../docs/adrs/0003-spaced-repetition-scheduling-policy-accepted.md)
lists trustworthy Grades as a prerequisite and defines the excluded attempt;
this plan measures the prerequisite and changes neither.
[ADR 0007](../../../docs/adrs/0007-environments-and-isolation-accepted.md)
prohibits test-only access to Production, so the verifier replay builds its
requests in the Unit Test environment and sends them to the model provider
directly; it never calls the Production contest operation. The ADR index
and records agree; no conflict or supersession was found. No North Star
topic governs this validation and none is added.

The replay gives the verifier the focus note only, without linked notes.
The generation rules require the correct answer to be supported by the
focus note alone, so the key does not depend on linked notes. The
verifier's judgments about relevance to linked notes can differ from
Production; each verifier result records this limit.

  `Mcq.checkAnswer` compares positions only.

  `GeneratedMcq` carries the answer text and distractors, and
